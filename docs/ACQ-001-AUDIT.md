# ACQ-001 — Audit SEO et conversion

Audit du 28 novembre 2026. Sources lues sur `main` au commit `e79aaa616479523c47b5543556dfa930c6ffc789`. Les sondages de production ont ciblé `https://kagekuni.com`. Le build local et la production présentent des noms différents pour le module JavaScript principal. Les observations ci-dessous distinguent donc les deux environnements.

## État vérifié dans le dépôt

| Sujet | Constat |
| --- | --- |
| Pages et navigation | `frontend/src/router/index.js` définit cinq routes publiques, `/`, `/rules`, `/legal`, `/login` et `/register`. La landing est **`/`**. `/home` est le hub authentifié. Le garde attend `GET /api/auth/me` lors de la première navigation, y compris sur les pages publiques. Sans session, il redirige le hub vers `/` côté client. Un compte sans personnage est dirigé vers `/character-creation`. Aucune route générique de 404 n'est définie. |
| Contenu | `LandingView.vue` présente le jeu et propose deux CTA, essai invité et inscription. La vue comporte un H1, des sections sur le deck et la progression, et des liens vers les règles. `RulesView.vue` sélectionne le Markdown FR ou EN dans `frontend/src/content/`. Les liens de section utilisent des identifiants communs et des alias localisés. Conserver ces liens lors de toute évolution des URL. |
| Langues | `i18n.js`, `utils/localeStorage.js` et `LocaleSwitcher.vue` basculent la langue dans Vue et la mémorisent dans le navigateur. Le français est la langue par défaut. Les deux variantes partagent les mêmes URL. |
| Métadonnées | `frontend/index.html` fixe `lang="fr"`, le titre générique « Kagekuni », la favicon, le viewport et la couleur de thème. La recherche dans les sources frontend/backend et la configuration de déploiement n'a trouvé ni description par page, ni canonical, ni hreflang, ni Open Graph, ni JSON-LD, ni fichiers robots/sitemap prévus pour la publication. |
| Vite, Docker et Nginx | `frontend/vite.config.js` compile une SPA. `Dockerfile` copie `frontend/dist` dans l'image de production. `docker/nginx.conf` relaie `/api/` vers Node et utilise `try_files $uri $uri/ /index.html` pour le reste. Cette règle couvre aussi les chemins inconnus et les fichiers absents. |
| Poids et structure | Les importations directes de nombreuses vues privées dans le routeur accroissent le coût du point d'entrée public. Le build local produit un module principal de 910,08 kB (281,41 kB gzip), un module préchargé de 116,73 kB (44,96 kB gzip) et 276,91 kB de CSS (48,92 kB gzip). Le build signale un chunk supérieur à 500 kB. La landing utilise des illustrations WebP, charge l'image sous la ligne de flottaison en différé et prévoit des styles mobiles et de mouvement réduit. |
| Invité et inscription | Le CTA invité appelle `POST /api/auth/guest` avec la langue de l'interface, puis navigue vers `/home`. Le serveur crée un utilisateur et un profil invité avec une durée de sept jours. L'inscription par courriel utilise `POST /api/auth/register`. La vue propose aussi Google. Pour un invité existant, `AppLayout.vue` ouvre le formulaire de conversion. Le service de conversion par courriel met à jour le même identifiant utilisateur. |
| Mesure | La recherche de marqueurs courants (analytics, UTM, gtag, Plausible, PostHog, Matomo, sendBeacon, Web Vitals) n'a trouvé aucune instrumentation frontend/backend d'acquisition ou d'entonnoir. Les états métier en base et la télémétrie d'infrastructure visible dans les en-têtes HTTP ne mesurent pas la conversion visite → partie. Les outils externes et les données de trafic restent à vérifier avec le propriétaire. |

## Observations en production

- Les réponses HTTP finales pour `/`, `/home`, `/rules`, `/legal`, `/login`, `/register`, `/robots.txt`, `/sitemap.xml`, `/fr/home`, `/en/home` et une URL inconnue sont des réponses 200 de type `text/html`. Les onze réponses HTML ont le même SHA-256. Le HTML brut contient un élément `#app` vide et le titre générique. Les chemins robots et sitemap servent donc le shell HTML. L'URL inconnue constitue un risque de soft 404 à confirmer dans Search Console.
- `GET /api/auth/me` sans session répond 401 en JSON. Ce résultat et les sondages HTML concordent avec la séparation des réponses navigateur/API dans le code.
- Chromium en production, profil Pixel 7 (412 px CSS) : H1 et CTA affichés, aucun débordement horizontal à cette largeur, premier lien de connexion atteignable au clavier. Le menu s'ouvre et se ferme avec Échap. L'analyse axe WCAG A/AA exécutée sur l'accueil FR fermé n'a signalé aucune violation. Le code de `SlidePanel.vue` ne gère pas explicitement la mise au focus, son confinement et sa restitution. Un test clavier complet et un test au lecteur d'écran restent nécessaires.
- Après sélection de l'anglais sur la landing, le H1 devient anglais, mais l'URL reste `/` et le document conserve `lang="fr"`. Le CTA secondaire ouvre ensuite `/register` avec EN présélectionné. Sur desktop, l'ouverture anonyme de `/home` aboutit à `/`, et `/rules` affiche les règles.
- Deux premières visites mobiles synthétiques affichent un LCP d'environ 2,76 s et 1,81 s. La requête de session prend environ 207 et 191 ms sur ces essais. Ces deux observations sans protocole de throttling ne permettent aucune conclusion sur les Core Web Vitals de terrain.
- Parcours invité testé avec réponses API interceptées dans Chromium : clic sur le CTA, requête `POST /api/auth/guest` avec `{"language":"fr"}`, puis arrivée à `/character-creation` lorsque l'API simulée indique l'absence de personnage.

## Choix du rendu public

| Approche | Intérêt | Coût et risque |
| --- | --- | --- |
| Prérendu statique au build | Produit un HTML FR/EN complet pour un petit ensemble fini de pages. Réutilise le service de fichiers Nginx et garde l'application privée en SPA. Une mise à jour éditoriale suit le cycle de livraison existant. | Il faut une source commune pour le contenu et les métadonnées, tester les liens et la correspondance entre HTML et Vue, et garder la génération indépendante des cookies et de l'API. Le bootstrap actuel utilise `window` et le garde amorce l'authentification. Isoler l'entrée publique ou injecter un état déterministe pendant la génération. |
| SSR Vue à la requête | Peut répondre avec du HTML à partir de données fraîches, si un futur catalogue public en a besoin. | Ajoute une exécution serveur, des règles de cache, des tests d'hydratation et une séparation stricte des données publiques et de session. Les pages publiques actuelles peuvent être générées sans données par visiteur. |

Le prérendu statique est recommandé pour l'accueil et les règles. Réévaluer le SSR si une demande validée exige des pages publiques dynamiques dont le volume ou la cadence dépasse ce que le build peut gérer.

Les risques principaux sont une mauvaise canonicalisation des variantes, des liens cassés ou des chemins privés exclus par une règle Nginx trop large, une divergence entre le HTML généré et la SPA, et un biais d'attribution lié aux essais ou aux comptes invités expirés. La validation devra aussi inclure l'inspection des URL et du sitemap dans Search Console, l'état de l'indexation, les aperçus de partage sur les plateformes et, si les données existent, les mesures de terrain. Les chiffres de conversion, l'activation réelle et la rétention demandent des données ou des tests supplémentaires.

## Tests et limites

- Lecture de `AGENTS.md`, `README.md`, `docs/GAME_RULES.md`, du routeur, des vues publiques, des chemins d'authentification, de Vite et de la chaîne Docker/Nginx. Recherche de marqueurs SEO et analytiques dans les sources.
- `npm ci --prefix frontend` et `npm run build --prefix frontend` réussis sur le commit audité. Aucun test de gameplay nécessaire pour cet audit documentaire.
- Sondages `curl` des URL ci-dessus, comparaison des corps et inspection de l'HTML brut.
- Chromium en production sur mobile émulé et desktop, contrôle axe sur l'accueil FR et simulation d'API pour l'invité. Aucun compte ni personnage créé en production. La persistance de session, la soumission d'inscription, Google, l'expiration, la conversion et la première mission restent à tester de bout en bout dans un environnement isolé. Search Console, données analytiques, mesures terrain et validation complète d'accessibilité restent à vérifier.
- Fichiers modifiés pour cet audit : `docs/ACQUISITION.md` et le présent rapport. Aucun changement applicatif, aucune fusion et aucun déploiement.
